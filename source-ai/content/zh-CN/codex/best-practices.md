# Codex 最佳实践

如果你是 Codex 或编程代理的新手，本指南将帮助你更快获得更好的结果。它涵盖让 Codex 在 [CLI](/codex/cli)、[IDE 扩展](/codex/ide) 和 [ChatGPT 桌面应用](/codex/app) 中更有效的核心习惯，从提示和规划到验证、MCP、技能和计划任务。

当你把 Codex 不太当作一次性助手，而更像一个可以持续配置和改进的队友时，它的效果最好。

一种有用的思考方式是：从适合任务的上下文开始，使用 `AGENTS.md` 提供持久指导，配置 Codex 以匹配你的工作流，用 MCP 连接外部系统，把重复性工作变成技能，并自动化稳定的工作流。

## 强有力的首次使用：上下文与提示

即使你的提示并不完美，Codex 也已经强大到足以派上用场。你常常可以在最少设置下交给它一个难题，仍然得到很强的结果。清晰的 [提示](/codex/prompting) 并不是获得价值的必要条件，但它确实会让结果更可靠，尤其是在更大的代码库或更高风险的任务中。

如果你在大型或复杂的仓库中工作，最大的突破点是给 Codex 提供适合任务的上下文，并为你想要完成的事情提供清晰结构。

一个好的默认做法是在提示中包含四件事：

- **目标：** 你想改变或构建什么？
- **上下文：** 哪些文件、文件夹、文档、示例或错误与这个任务有关？你可以 @ 提及某些文件作为上下文。
- **约束：** Codex 应该遵循哪些标准、架构、安全要求或约定？
- **完成标准：** 任务完成前应满足什么条件，例如测试通过、行为改变，或某个 bug 不再复现？

这有助于 Codex 保持范围清晰、减少假设，并产出更容易审查的工作。

根据任务难度选择推理级别，并测试什么最适合你的工作流。不同的用户和任务最适合不同的设置。

- 低：用于更快、范围明确的任务
- 中或高：用于更复杂的更改或调试
- 超高：用于长时间、代理式、推理繁重的任务

为了更快提供上下文，可以尝试在 ChatGPT
桌面应用中使用语音听写，口述你想让 Codex 做什么，而不是打字输入。

## 困难任务先规划

如果任务复杂、含糊，或难以描述清楚，让 Codex 在开始编码前先规划。

有几种方法效果很好：

**使用计划模式：** 对大多数用户来说，这是最简单也最有效的选项。计划模式让 Codex 在实现前收集上下文、提出澄清问题，并构建更强的计划。用 `/plan` 或 Shift+Tab 切换。

**让 Codex 采访你：** 如果你对想要什么只有粗略想法，但不确定如何描述清楚，先让 Codex 向你提问。告诉它挑战你的假设，并在写代码前把模糊想法变成具体方案。

**使用 PLANS.md 模板：** 对于更高级的工作流，你可以配置 Codex 在长时间运行或多步骤工作中遵循 `PLANS.md` 或执行计划模板。更多细节请参见 [执行计划指南](/cookbook/articles/codex_exec_plans)。

## 让指导可复用，借助 `AGENTS.md`

一旦某个提示模式奏效，下一步就是停止手动重复它。这就是 [AGENTS.md](/codex/agent-configuration/agents-md) 的用武之地。

可以把 `AGENTS.md` 看作面向代理的开放格式 README。它会自动加载到上下文中，也是编码你和团队希望 Codex 如何在仓库中工作的最佳位置。

一份好的 `AGENTS.md` 应涵盖：

- 仓库布局和重要目录
- 如何运行项目
- 构建、测试和 lint 命令
- 工程约定和 PR 期望
- 约束和禁止事项规则
- “完成”意味着什么，以及如何验证工作

CLI 中的 `/init` 斜杠命令是快速启动命令，用于在当前目录中搭建一个起始 `AGENTS.md`。它是很好的起点，但你应该编辑生成结果，使其匹配团队实际构建、测试、审查和发布代码的方式。

你可以在不同层级创建 `AGENTS.md` 文件：放在 `AGENTS.md` 中、用于个人默认值的全局 `~/.codex`；用于共享标准的仓库级文件；以及子目录中用于本地规则的更具体文件。如果离当前目录更近的位置存在更具体的文件，则该指导优先。

保持实用。简短而准确的 `AGENTS.md` 比充满模糊规则的长文件更有用。从基础开始，只有在你注意到重复错误后才添加新规则。

如果 `AGENTS.md` 开始变得太大，保持主文件简洁，并引用针对特定任务的 markdown 文件，例如规划、代码审查或架构。

当 Codex 两次犯同样错误时，请它做复盘并更新
`AGENTS.md`。指导会保持实用，并基于真实摩擦。

## 配置 Codex 以保持一致性

配置是让 Codex 跨会话和跨界面表现更一致的主要方式之一。例如，你可以为模型选择、推理力度、沙箱模式、批准策略、配置文件和 MCP 设置默认值。

一个好的起始模式是：

- 将个人默认值保存在 `~/.codex/config.toml` 中（在 ChatGPT 桌面应用中为 **设置 > 配置 > 打开 config.toml**）
- 将仓库特定行为保存在 `.codex/config.toml` 中
- 仅在一次性场景中使用命令行覆盖（如果你使用 CLI）

[`config.toml`](/codex/config-file/config-basic) 用于定义持久偏好，例如 MCP 服务器、多代理设置和功能开关。特定配置文件的覆盖项存放在单独的 `$CODEX_HOME/profile-name.config.toml` 文件中。

Codex 自带操作系统级沙箱，并有两个你可以控制的关键旋钮。批准模式决定 Codex 何时请求你允许运行命令，沙箱模式决定 Codex 是否能在目录中读取或写入，以及代理能访问哪些文件。

如果你刚接触编码代理，请从默认权限开始。默认保持严格的批准和沙箱设置，只有在需求明确后，才为受信任的仓库或特定工作流放宽权限。

请注意，CLI、IDE 扩展和 ChatGPT 桌面应用共享相同的配置层级。可在 [示例配置](/codex/config-file/config-sample) 页面了解更多。

尽早为你的真实环境配置 Codex。许多质量问题
实际上是设置问题，比如工作目录错误、缺少写入权限、
模型默认值错误，或缺少工具和连接器。

## 通过测试和审查提高可靠性

不要止步于让 Codex 进行更改。让它在需要时创建测试，运行相关检查，确认结果，并在你接受之前审查工作。

Codex 可以为你完成这个循环，但前提是它知道“好”的标准。该指导可以来自提示词或 `AGENTS.md`。

这可以包括：

- 为更改编写或更新测试
- 运行正确的测试套件
- 检查 lint、格式或类型检查
- 确认最终行为符合请求
- 审查 diff 中的错误、回归或有风险的模式

在 ChatGPT 桌面应用中切换 diff 面板，即可直接本地[审查
更改](/codex/code-review?surface=app)。点击特定行
提供反馈，这些反馈会作为上下文传递给下一轮 Codex 对话。

一个有用的选项是斜杠命令 `/review`，它为你提供了几种审查代码的方式：

- 针对基础分支进行 PR 风格审查
- 审查未提交的更改
- 审查某个提交
- 使用自定义审查说明

如果你和你的团队有一个 `code_review.md` 文件，并在 `AGENTS.md` 中引用它，Codex 在审查时也会遵循该指导。对于希望审查行为在各个仓库和贡献者之间保持一致的团队来说，这是一种强大的模式。

Codex 不应只是生成代码。配合正确的指令，它还可以帮助**测试代码、检查代码和审查代码**。

如果你使用 GitHub Cloud，可以设置 Codex 为你的 PR 运行[代码审查](/codex/third-party/github)。在 OpenAI，Codex 审查了 100% 的 PR。你可以启用自动审查，或者在你 @Codex 时让它响应式地进行审查。

## 使用 MCP 获取外部上下文

当 Codex 所需的上下文位于代码仓库之外时，请使用 MCP。它让 Codex 能够连接到你已经在使用的工具和系统，这样你就不必不断地把实时信息复制粘贴到提示词中。

[模型上下文协议](/codex/extend/mcp)（Model Context Protocol，简称 MCP）是一个用于将 Codex 连接到外部工具和系统的开放标准。

在以下情况下使用 MCP：

- 所需的上下文位于代码仓库之外
- 数据频繁变化
- 你希望 Codex 使用工具，而不是依赖粘贴的指令
- 你需要跨用户或跨项目的可重复集成

Codex 同时支持 STDIO 和带 OAuth 的 Streamable HTTP 服务器。

在 ChatGPT 桌面应用中，前往 **Settings > MCP servers** 查看自定义和推荐的服务器。通常，Codex 可以帮助你安装所需的服务器。你只需开口询问即可。你也可以在 CLI 中使用 `codex mcp add` 命令，通过名称、URL 和其他详细信息添加你的自定义服务器。

只有在工具能解锁真正的工作流程时才添加它们。不要一开始就接入
你使用的每一个工具。先从一两个能明显省去你经常手动
重复操作的工具开始，然后再逐步扩展。

## 将可重复的工作转化为技能

一旦某个工作流程变得可重复，就不要再依赖冗长的提示词或反复的来回沟通。使用一个 [技能](/codex/build-skills)，将说明打包在一个 `SKILL.md` 文件中，同时包含上下文和支持逻辑，以便 Codex 始终如一地应用。技能可以在 CLI、IDE 扩展和 ChatGPT 桌面应用中使用。

让每个技能只专注于一项任务。从 2 到 3 个具体的用例开始，定义清晰的输入和输出，并撰写好描述，使其说明该技能的作用以及何时使用它。要包含用户实际上会说出的触发短语类型。

不要试图一开始就覆盖所有边缘情况。先从一个有代表性的任务入手，把它做好，然后将该工作流程转化为技能，再在此基础上逐步改进。只有当脚本或额外资源能提高可靠性时才包含它们。

一个很好的经验法则是：如果你一直在重复使用同一个提示词，或者反复纠正同一个工作流程，那它很可能就应该成为一个技能。

技能对于以下这类重复性工作尤其有用：

- 日志分类
- 发布说明起草
- 对照清单进行 PR 审查
- 迁移规划
- 遥测或事件摘要
- 标准调试流程

`$skill-creator` 技能是搭建技能第一个版本的最佳起点。在迭代过程中，将第一个版本保留在本地。当它准备好被广泛共享时，将其打包为一个 [插件](https://developers.openai.com/plugins/build/plugins)。技能中最重要的部分之一是描述。它应该说明该技能的作用以及何时使用它。

个人技能存储在 `$HOME/.agents/skills` 中，而团队共享的技能
可以提交到仓库内的 `.agents/skills` 中。这对于
帮助新队友快速上手尤其有帮助。

## 对重复性工作使用定时任务

一旦工作流程稳定下来，你就可以安排 Codex 在后台为你运行它。在 ChatGPT 桌面应用中，[定时任务](/codex/automations) 允许你为重复性工作选择项目、提示词、运行频率和执行环境。

从 **Scheduled**（定时）页面创建一个定时任务。选择项目、提示词、
运行频率，以及任务是在专用的 Git 工作树中运行还是在你的本地
环境中运行。提示词可以调用技能。了解更多关于
[Git 工作树](/codex/environments/git-worktrees) 的信息。

合适的候选任务包括：

- 总结最近的提交
- 扫描可能的 bug
- 起草发布说明
- 检查 CI 失败
- 生成站会摘要
- 按计划运行可重复的分析工作流

一个有用的原则是：技能定义方法，而定时任务定义时间安排。如果一个工作流程仍需要大量引导，请先将其转化为技能。一旦它变得可预测，为其设定日程就可以节省时间。

将定时任务不仅用于执行，还用于反思和维护。回顾
最近的对话，总结反复出现的阻碍，并随着时间推移改进提示词、说明
或工作流程设置。

## 组织长时间运行的聊天

聊天会随着时间积累上下文、决策和操作，因此妥善管理它们对质量有很大影响。

ChatGPT 桌面应用允许你固定聊天并创建工作树。如果你使用
CLI，这些 [斜杠命令](/codex/developer-commands?surface=cli) 尤其有用：

- `/experimental` 用于切换实验性功能并添加到你的 `config.toml`
- `/resume` 用于恢复已保存的聊天
- `/fork` 用于创建新聊天，同时保留原始对话记录
- `/compact` 当聊天变得很长并且你想要早期上下文的摘要版本时使用。Codex 也会自动压缩聊天
- `/agent` 当你运行多个并行代理并想在活动的代理线程之间切换时使用
- `/theme` 用于选择语法高亮主题
- `/apps` 用于在 Codex 中直接使用 ChatGPT 应用
- `/status` 用于检查当前会话状态

每个连贯的工作单元保持一个聊天。如果工作仍然属于同一个
问题，留在同一个聊天中通常更好，因为它保留了推理
轨迹。只有当工作真正产生分支时才分叉。

使用 Codex 的 [子代理](/codex/agent-configuration/subagents) 工作流，将
有界的工作从主线程卸载出去。让主代理专注于
核心问题，并使用子代理处理探索、测试或分类等任务。

## 常见错误

首次使用 Codex 时应避免的几个常见错误：

- 在提示中塞入过多持久性规则，而不是将它们移入 `AGENTS.md` 或技能中
- 没有让代理看到自己的工作，因为没有提供如何最好地运行构建和测试命令的详细信息
- 在多步骤和复杂任务上跳过规划
- 在理解工作流之前就授予 Codex 对你计算机的完全权限
- 在不使用 Git 工作树的情况下对相同文件运行实时任务
- 在任务手动运行尚不可靠之前就安排周期性任务
- 把 Codex 当作需要逐步盯着的东西，而不是与自己的工作并行使用
- 整个项目只用一个聊天，而不是每个连贯的结果一个聊天。这会导致上下文臃肿，随着时间推移结果更差
